# Architecture

How the SCB POC interpreter is put together, for someone opening the code for the first time. The language itself is defined in `SPEC.md`; milestones are in `POC_PLAN.md`.

## The pipeline

```
 .scb files ──► SourceMap ──► lex ──► tokens ──► parse ──► AST ──► check ──► Program ──► Isolate::run
               (scb-syntax)  (scb-syntax)       (scb-syntax)      (scb-types)            (scb-runtime)
```

| Stage | Crate | Entry point | Status |
| --- | --- | --- | --- |
| Load files | `scb-cli` | `load()` | done (M0) |
| Source map, spans, diagnostics | `scb-syntax` | `SourceMap`, `Span`, `Diagnostic` | done (M0) |
| Lexer | `scb-syntax` | `lex()` | done (M1) |
| Parser and AST | `scb-syntax` | `parse()`, `parse_source()`, `ast` | done (M2) |
| Name resolution, type checking | `scb-types` | `check()` → `Program` (typed IR) | done (M3) |
| Interpreter, values, refcounting | `scb-runtime` | `Isolate::run()` | M4 (destructors, runtime exclusivity: M5) |
| Core library | `scb-stdlib` | `natives()` | M4 (the stub API), M7 (rest) |
| Conformance runner | `scb-conformance` | `cargo run -p scb-conformance` | done (M0) |

Each stage reports problems as `Diagnostic`s (a stable `kind`, a message, a `Span`, optional notes and a fix-it; the kinds are listed in `DIAGNOSTICS.md`) and keeps going where it can, so a single run shows every independent error. A later stage runs only when the earlier ones produced no errors.

## Source files and positions (`scb-syntax/src/source.rs`)

All files of one compilation live in a `SourceMap`; a `FileId` names one. Every token and AST node carries a `Span`: a file id plus a byte range (`u32` offsets, so files are limited to 4 GiB). Line and column numbers are computed only when a diagnostic is printed (`SourceFile::line_col`, columns in codepoints).

## Lexer (`scb-syntax/src/lexer.rs`, `token.rs`)

A hand-written, context-free scanner. It produces `Token { kind, span }` values ending in `Eof`. Literals are decoded during lexing: escapes are resolved, numbers become values, and double-quoted strings and heredocs are split into text, `$name` and `{$expr}` parts. The `{$expr}` parts are tokenized by the lexer calling itself. Keywords are an enum generated by a macro from the SPEC list; type names such as `int` are ordinary identifiers.

## Parser (`scb-syntax/src/parser/`, `ast.rs`)

Recursive descent for declarations and statements, with Pratt-style precedence climbing for binary operators. `parser/mod.rs` explains the cursor, error recovery and depth limits; `parser/expr.rs` explains the precedence levels. The output is the AST in `ast.rs`, which mirrors SPEC "Grammar sketch". Removed PHP syntax and out-of-scope features are reported but never appear in the tree.

`dump.rs` prints the AST as an S-expression. The golden tests in `scb-syntax/tests/golden/` compare that dump against checked-in `.ast` files; they cover every code block in `SPEC.md`.

## Checker (`scb-types`)

`check()` runs these passes over the parsed user files and the stdlib stubs:

1. **Stdlib stubs** (`crates/scb-types/stdlib/*.scb`, plus the numeric types generated in `stdlib.rs`) declare the core library in SCB syntax. They are parsed in *stdlib mode*, which allows generics, `where` bounds and bodiless (native) functions. `namespace Prelude;` is the root namespace. The checker treats stdlib signatures exactly like user code, so `$list->push('a')` on a `list<int>` is an ordinary `type-mismatch`.
2. **Collection** (`collect.rs`): register every name (types, functions and constants live in separate tables, as in PHP), then resolve headers (parents, interfaces, type parameters), then members (fields with inherited layout, methods, constants, statics, enum cases). Name lookup follows `resolve.rs`: `use` alias, then the file's namespace, then the prelude.
3. **Validation** (`validate.rs`): class-level rules (`final`, overrides, abstract methods, interface defaults) and the definite-assignment analysis of constructors (`uninitialized-property`).
4. **Bodies** (`check/`): each function, method, closure and initializer is checked into the **TIR** (`tir.rs`). The TIR is the program the interpreter runs: every expression has its type, locals are numbered frame slots, calls name their target and list their arguments by parameter index in written order, assignment targets are places with a type at every level (for copy-on-write), and `?->` chains are explicit. `check/mod.rs` explains frames, captures and flow typing; each submodule documents its own rules.

Types are interned (`ty.rs`): a `Ty` is a small integer, unions are normalized, and `?T` is `T|null`.

## The compiler thread (`scb-types/src/lib.rs`)

`scb_types::check()` runs the whole front end on its own thread with a 64 MiB stack. The parser and checker are recursive. The parser caps tree depth at 512 levels (`too-deeply-nested`), and the large stack makes sure that depth fits even in debug builds, whose stack frames are several times larger. The caller's own stack size therefore never matters.

## Runtime (`scb-runtime`)

All interpreter state lives in an `Isolate`. Nothing is global; this is CLAUDE.md architecture rule 1. The isolate owns its stdout, stderr, stdin and environment as injected handles (`IsolateIo`): only the CLI connects real OS handles, and a later FastCGI server can give each request its own. Stdout is buffered and flushed before stdin reads and on exit. The compiled `Program` is immutable and shared as `Arc<Program>`, so one compilation can serve many isolates.

**Values** (`value.rs`): primitives are stored inline (`I8(i8)` … `F64(f64)`, `Bool`). Strings, bytes, lists, maps, sets, tuples, structs and enums with payloads sit behind an `Rc` and are copy-on-write through `Rc::make_mut`: a write copies only a shared level. Class instances are `Rc<RefCell<…>>`.

**Interpreter** (`interp/`): a tree-walking evaluator over the TIR.
- *Errors.* Every evaluation returns `Result<_, Flow>`, where `Flow` is a thrown value, `exit`, `return`, `break`/`continue`, a fatal error or `abort`.
- *Writes* (`interp/place.rs`). A write evaluates the place's path first, then the right side, then walks the path making each value level unique.
- *Moves.* `inout` arguments and `mutating` receivers move their value into the callee's frame and back out (also after a throw), so the callee mutates an unshared value in place. A loop of `push` is therefore O(n) (`scb-stdlib/tests/run.rs` guards this).
- *Integers.* Integer operations compute in `i128` and trap on overflow.

**Core library** (`scb-stdlib`): native functions registered by the names the checker gives stub declarations (`list.push`, `i8::wrap`, `Io\print`). The CLI hands them to the isolate (`Isolate::with_natives`), so the runtime does not depend on the stdlib.

**Stack.** SCB calls recurse in Rust. The runtime caps call depth (a fatal "stack overflow" error, as the spec requires), and the CLI runs programs on a thread with a 1 GiB stack (reserved, only touched pages are committed), so the cap is reached before the Rust stack is.

## Tests

| Kind | Where | What |
| --- | --- | --- |
| Unit tests | next to the code (`lexer_tests.rs`, `parser_tests.rs`, `mod tests`) | single behaviours, error kinds, spans |
| Golden AST tests | `scb-syntax/tests/golden.rs` | parser output for grammar samples and every SPEC code block (`SCB_BLESS=1` to update) |
| Repository tests | `scb-syntax/tests/repository.rs` | every `.scb` file in the repo lexes and parses as its header expects, and broken inputs never panic |
| Conformance | `tests/conformance/`, run by `scb-conformance` | end-to-end through the `scb` binary: expected stdout, exit codes and compile-error kinds |

Run everything with `cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test && cargo run -p scb-conformance`.
